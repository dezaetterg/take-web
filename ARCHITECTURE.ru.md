# Архитектура TakeWeb

Документ описывает внутреннее устройство, модель изоляции процессов, графический конвейер и алгоритмы управления ресурсами в TakeWeb.

## 1. Модель процессов и изоляция

TakeWeb построен на базе многопроцессной архитектуры WebKitGTK 6.0 с разделением привилегий и адресных пространств.

```
+------------------------------------------------------------------------+
|                      UI Process (takeweb)                             |
|  - Главный поток GTK4 / Libadwaita                                     |
|  - Управление окнами, вкладками, боковой панелью, адресной строкой    |
|  - Планировщик MemoryManager                                           |
|  - Асинхронный воркер базы данных (AsyncDb)                            |
+------------------------------------------------------------------------+
         |                                           |
         | IPC (Unix Sockets)                        | IPC (Unix Sockets)
         v                                           v
+-----------------------------+       +----------------------------------+
|   WebKitNetworkProcess      |       |      WebKitWebProcess            |
|  - Сетевой стек, сокеты     |       |  (в песочнице Bubblewrap / bwrap)|
|  - HTTP дисковый кеш (LRU)  |       |  - Парсер HTML / CSS             |
|  - Cookie и HSTS хранилище  |       |  - Движок JavaScriptCore         |
|  - WebKit Content Filter    |       |  - Растеризатор Skia             |
+-----------------------------+       +----------------------------------+
```

### 1.1. Процесс интерфейса (UI Process)
Является координатором приложения. Выполняет:
* Рендеринг элементов графического окружения средствами GTK4 и Libadwaita.
* Маршрутизацию действий пользователя между вкладками.
* Управление персистентным состоянием через базу данных SQLite. Все операции записи вынесены из потока интерфейса в выделенный рабочий поток `AsyncDb` через канал сообщений `std::sync::mpsc`.

### 1.2. Сетевой процесс (WebKitNetworkProcess)
Выполняет обработку сетевых протоколов отдельно от парсинга веб-страниц:
* Хранит кеш DNS, TLS-сессии и дисковый кеш HTTP.
* Ограничивает размер дискового кеша жестким лимитом 500 МБ. Фоновый поток выполняет асинхронную ротацию каталога кеша по алгоритму LRU.
* Содержит скомпилированные байткод-правила блокировки трекеров и рекламы (`WebKitUserContentFilterStore`). Фильтрация выполняется на фазе сетевого запроса до передачи тела ответа в процесс рендеринга.

### 1.3. Процесс веб-содержимого (WebKitWebProcess)
Исполняет недоверенный сетевой код страниц. Защищен песочницей Bubblewrap (`bwrap`):
* Доступ к локальной файловой системе изолирован. Допускается чтение только разрешенных системных путей (шрифты, иконки, темы оформления, библиотеки DRI).
* Прямые переходы на локальные адреса `file://` со страниц Интернета блокируются движком.
* Доступ к внутренним протоколам браузера (`take://*`) защищен валидацией криптографически стойкого сессионного токена, предотвращающего спуфинг служебных страниц со стороны открытых сайтов.

## 2. Управление оперативной памятью

Система контроля ресурсов минимизирует удержание оперативной памяти неактивными вкладками.

### 2.1. Алгоритм MemoryManager
Жизненный цикл каждой вкладки отслеживается через структуру `TrackedTab`:
* Активная вкладка: отображается в интерфейсе, имеет полный приоритет рендеринга.
* Фоновая вкладка: при переключении пользователя помечается как фоновая с фиксацией метки времени `Instant::now()`.
* Таймер опроса: каждые 5 секунд планировщик проверяет длительность простоя фоновых страниц.
  * Базовый таймаут: 30 секунд.
  * Аварийный таймаут: 10 секунд (активируется при объеме свободной RAM менее 15% либо при наличии более 4 фоновых вкладок).

При превышении таймаута выполняется выгрузка вкладки (`suspend_tab_internal`):
1. Вызов `view.set_visible(false)` для отключения планирования отрисовки в композиторе.
2. Очистка кеша декодированных растровых изображений и глифов шрифтов через `WebKitWebsiteDataManager::clear(WebsiteDataTypes::MEMORY_CACHE)`.
3. Принудительное выполнение сборки мусора в куче JavaScriptCore (`window.gc()`).
4. Приостановка воспроизведения аудио и видеоэлементов с сохранением текущей позиции воспроизведения.

При повторном обращении пользователя к вкладке рендерер активируется мгновенно (`resume_tab_internal`), восстанавливая видимость без перезагрузки документа по сети.

### 2.2. Калибровка WebKit MemoryPressure
На этапе запуска функция `detect_memory_pressure_plan` считывает параметры физической памяти из `/proc/meminfo` и выставляет лимиты подсистемы контроля памяти WebKit:

| Объем RAM устройства | Жесткий лимит WebKit | Порог предупреждения (Conservative) | Строгий порог (Strict) | Критический сброс (Kill) |
| :--- | :--- | :--- | :--- | :--- |
| До 4 ГБ | 768 МБ | 60% | 75% | 90% |
| От 4 до 8 ГБ | 1024 МБ | 65% | 80% | 92% |
| Свыше 8 ГБ | 1536 МБ | 70% | 85% | 95% |

## 3. Графический конвейер и аппаратное ускорение

Настройка графической подсистемы выполняется до инициализации GTK в модуле `browser::performance`:

```
[Старт takeweb]
       |
       v
[Определение GPU и сессии] ---> (NVIDIA + Wayland + Display)
       |
       +---> Расчет переменных среды (GDK_BACKEND, GSK_RENDERER, DMA-BUF)
       |
       +---> Необходим перезапуск процесса (re-exec)?
                 |
                 +---[Да]---> execve() с экспортированными переменными
                 |
                 +---[Нет]---> Инициализация GTK4 и WebKit
```

### 3.1. Аппаратный рендеринг через DMA-BUF
По умолчанию WebKitGTK на драйверах NVIDIA выставляет политику программного рендеринга. TakeWeb принудительно задает `WEBKIT_FORCE_DMABUF_RENDERER=1`. Это открывает доступ к узлу `/dev/dri/renderD128`, позволяя WebProcess передавать готовые буферы кадров напрямую в GPU-память процесса отображения (zero-copy sharing).

### 3.2. Обход задержек синхронизации Mutter
В сессиях Wayland на видеокартах NVIDIA обмен буферами WebKitGTK и композитора Mutter может приводить к взаимным блокировкам очередей синхронизации (GNOME Issue #3144), ограничивающим частоту кадров на уровне 20–30 FPS. TakeWeb маршрутизирует окно через мост Xwayland (`GDK_BACKEND=x11`, `GSK_RENDERER=gl`), отключая блокировку vblank со стороны клиента (`__GL_SYNC_TO_VBLANK=0`). Финальную синхронизацию и вывод на экран берет на себя композитор Wayland, обеспечивая стабильные 60–144+ FPS.

### 3.3. Многопоточная растеризация
* `WEBKIT_SKIA_CPU_PAINTING_THREADS=4`: параллельная растеризация тайлов и декодирование изображений на ядрах процессора.
* `WEBKIT_SKIA_GPU_PAINTING_THREADS=2`: выделенные потоки загрузки текстур в GPU.
* `WEBKIT_LAYERS_TILE_SIZE=512`: фиксированный размер тайла снижает количество служебных переключений контекста на мониторах с разрешением 2K и 4K.
* `WEBKIT_DISABLE_FRAME_RATE_LIMIT=1`: снимает искусственный ограничитель кадров WebKit для дисплеев с высокой частотой обновления (120, 144, 240 Гц).

## 4. Подсистема хранения данных

Вся информация пользователя хранится локально в базе данных SQLite:
* Путь к файлу: `~/.local/share/takeweb/browser.db`.
* Режим журнала: WAL (Write-Ahead Logging). Обеспечивает одновременное чтение из нескольких потоков без блокировки потока записи.
* Синхронизация: `PRAGMA synchronous = NORMAL` для баланса между сохранностью данных при сбоях питания и скоростью транзакций.
* Полнотекстовый поиск: виртуальная таблица `omnibox_fts` на базе SQLite FTS5 с триггерами автоматического обновления для закладок и истории. Поиск в адресной строке выполняется за время порядка единиц миллисекунд без предварительной загрузки всей истории в оперативную память.

## 5. Хранение Cookie и изоляция данных сайтов

* **Физическое расположение**: Все файлы cookies, localStorage, IndexedDB и HSTS-записи сохраняются изолированно системным менеджером `WebKitWebsiteDataManager` в каталоге `~/.local/share/takeweb/` (в файле SQLite `cookies.db`).
* **Абсолютная изоляция от репозитория (Zero-Repo)**: Каталог с профилем пользователя находится за пределами рабочей директории браузера в системном дереве XDG. Кроме того, все файлы баз данных, сессий и кешей строго исключены в `.gitignore`. Утечка куки в git-репозиторий исключена архитектурно.
* **Приватный режим (RAM Only)**: Для приватных окон создается полностью эфемерный контекст `WebKitWebsiteDataManager(is_ephemeral = true)`. Данные куки и кэша хранятся строго в оперативной памяти и безвозвратно уничтожаются при закрытии вкладки.
* **Политика защиты от трекеров**: Браузер форсирует `WebKitCookieAcceptPolicy::NoThirdParty`, предотвращая межсайтовое отслеживание (ITP).

## 6. Локальный нейросетевой переводчик Bergamot WASM

* **Zero-Cloud**: Перевод выполняется полностью офлайн без передачи текста сторонним API (Google, DeepL, Yandex).
* **Архитектура WebWorker**: Перевод страниц и выделенного текста осуществляется через инкапсулированный WebWorker с движком Mozilla Bergamot WASM.
* **Хранилище моделей**: Бинарные веса моделей скачиваются по требованию пользователя в `~/.local/share/takeweb/models/bergamot/` и раздаются локально через зарегистрированную схему `take://models/`.

## 7. Дополнительные подсистемы

* **Reader Mode (Режим чтения)**: Движок парсинга DOM отсекает рекламные блоки, скрипты и медиа, предоставляя чистый структурированный текст с поддержкой светлой/тёмной темы.
* **Split View (Разделенный экран, F3 / Ctrl+\)**: Векторное разбиение рабочего пространства через `GtkPaned` с независимыми процессами и возможностью быстрого выбора вкладки.
* **PWA / App Mode (`--app=<URL>`)**: Компактный запуск веб-приложений без панелей навигации и генератор системных ярлыков `.desktop` в `~/.local/share/applications/`.
* **Локализация (i18n)**: Встроенные ресурсы `en.json` и `ru.json` со сквозным контролем паритета ключей через модульные тесты и динамическим определением системного языка.
* **Встроенная тема иконок TakeWeb**: 63 символьных SVG-иконки встроены в бинарник и автоматически распаковываются/регистрируются для GTK4, гарантируя одинаковый и полный вид интерфейса на любом DE и оконном менеджере (Hyprland, Sway, KDE, i3, XFCE).
